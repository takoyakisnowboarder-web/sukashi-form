# スカシフォーム 企画設計書 v1.1

作成日: 2026-07-17 / 更新: 2026-07-17（アプリ名確定・対象競技拡大・競合調査を反映）

**アプリ名: スカシフォーム**

- 表記は**カタカナを正式名称**とする。
- 漢字表記「透かしフォーム」は使わない。日本語のアプリ文脈では
  「透かし＝ウォーターマーク」「フォーム＝入力フォーム」と読まれ、
  *画像に透かしを入れる入力フォーム* と誤読されるため。
- 名称重複チェック済み（2026-07-17）: App Store / Google Play / 商標いずれも同名なし。
  ただし出願前に弁理士による正式調査を推奨。

## 1. 概要

スポーツの一瞬の動作を、**2本の映像を半透明で重ねて比較**するスマホアプリ。
「1ヶ月前の自分」と「今日の自分」、「決まった時」と「失敗した時」を重ねて、動きの違いを目で見て把握する。

### 想定シーン

- ゴルフ・野球などの**スイング**（1〜3秒）
- スノーボードの**キッカーの抜け**（数秒）
- **KINGS等の屋内練習施設**でのトレーニング（数秒）

いずれも「数秒の一瞬の動作を、繰り返し撮って前回と見比べる」という同じ構造。
クリップが短いため、フレーム展開方式（2.1）がそのまま無理なく使える。

### コアバリュー

「重ねて比較する」機能自体は既存アプリにも存在する（後述の競合参照）。
**差別化は以下の3点に絞る。**

1. **競技を選ばない** — ゴルフ特化アプリはブランドの無料アプリが強い。
   スノーボードのような領域には無料の巨人が来ない。ここが主戦場。
2. **フレーム単位で正確なコマ送り** — 技術方式（2.1）で担保する。
3. **買い切りのシンプルさ** — 広告なし・サブスクなし・アカウントなし・機能を盛らない。

### 競合（2026-07-17 時点の調査）

| アプリ | 重ね合わせ | 価格 | 対象 |
|---|---|---|---|
| ブリヂストンゴルフ公式 | あり（上下・左右・重ね） | 無料 | ゴルフ |
| V1 Golf | あり（上下・重ね） | - | ゴルフ |
| Athlete Crowd | あり | - | 複数スポーツ |

**結論: ゴルフ領域では戦わない。** 名前にも競技名を入れない。

## 2. 技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| フレームワーク | **Flutter** | 1コードベースでiOS/Android。UIが両OSでブレにくい |
| 撮影 | `camera` プラグイン | グリッド重畳はFlutter側のWidgetで実装 |
| 映像取り込み | `image_picker` | 端末標準カメラのスロー撮影映像を取り込める（重要） |
| フレーム展開 | **ネイティブ実装（Pigeon経由）** | 後述。ここが技術的な肝 |
| 保存 | `path_provider` + JSONファイル | 件数が少ないのでDB不要 |
| 状態管理 | Riverpod | 画面数が少ないので過剰にしない |

### 2.1 フレーム展開方式（設計上の最重要判断）

**動画プレイヤーを2つ重ねて再生する方式は採用しない。**

理由: コマ送り時のフレーム精度が端末・コーデック依存でブレる。2本の同期も保証されない。
比較アプリでこれは致命的。

**採用する方式:**

映像を読み込んだ時点で、全フレームを**画像ファイルに展開してキャッシュ**する。
その後は単なる画像の重ね合わせになるため、コマ送りもスライダー操作も完全に正確かつ滑らか。

```
動画ファイル
  ↓ ネイティブのフレーム抽出API
フレーム画像（JPEG, 長辺1280pxに縮小）を連番でキャッシュディレクトリに保存
  ↓
Flutter側: Stack + Image.file を2枚重ねて Opacity で合成
```

**ネイティブ側の実装:**

| OS | 使用API |
|---|---|
| Android | `MediaMetadataRetriever#getFramesAtIndex`（API 28 / Android 9 以上） |
| iOS | `AVAssetImageGenerator#generateCGImagesAsynchronously` |

Flutter ↔ ネイティブの橋渡しは **Pigeon**（型安全なコード生成）を使う。
手書きのMethodChannelは型ミスの温床になるため使わない。

> **注意:** ffmpeg_kit_flutter は2025年に開発終了・バイナリ配布停止済み。使わないこと。

**メモリ/ディスク見積もり:**

- 3秒 × 60fps = 180フレーム/本
- 長辺1280pxのJPEG ≒ 150KB/枚 → 約27MB/本、2本で約54MB（ディスク）
- 表示は `Image.file` で都度読むため、メモリには数枚しか載らない
- Flutter の `imageCache` サイズは明示的に調整すること（デフォルトのままだと膨らむ）
- 展開済みキャッシュはクリップ削除時に必ず破棄する

**展開の上限:**

安全弁として、**1クリップ最大10秒 / 最大600フレーム**でカットする。
それを超える動画（撮影・取り込みの両方）は、範囲選択（トリミング）を先にさせる。

> **注意: 「録画の長さの上限」と「フレーム展開できる長さの上限」を混同しないこと。**
>
> | | 上限 | 理由 |
> |---|---|---|
> | 録画の長さ | 30秒 | 20秒の1080p動画でも40〜60MB程度。ストレージへの配慮のみで、技術的制約ではない |
> | フレーム展開 | **10秒 / 600フレーム** | 20秒×60fps=1200枚は約180MB/本（2本で360MB）。展開に数十秒かかりUXが壊れる |
>
> **この2つはトリミングで橋渡しする。** 自撮りでは位置に入って構えて動く時間の余裕が要るため、
> 長め（例: カウントダウン5秒 → 20秒録画）に撮れることには実用上の価値がある。
> その中から必要な数秒だけを切り出して展開する。**録画を10秒に縛ってはいけない。**

## 3. 画面構成

```
[ライブラリ] ──┬── [撮影]
               ├── [取り込み（端末の動画から）]
               └── 2本選択 ── [比較]  ← アプリの主役
```

### 3.1 ライブラリ画面

- 撮影済みクリップをサムネイルのグリッドで一覧
- 各クリップ: サムネイル / 撮影日時 / 長さ / メモ（任意の一言、例「ドライバー 調子○」）
- タップで選択（最大2本）。2本選ぶと「比較する」ボタンが出る
- 長押しで削除・リネーム
- 右下に FAB: 撮影 / 端末の動画から取り込み

### 3.2 撮影画面

- カメラプレビュー全画面
- **グリッドオーバーレイ**（Flutter の CustomPaint で描画）
  - 種類: 格子（3×3 / 4×4）／十字／三分割／なし
  - 切替はワンタップ
- グリッド設定は保存され、次回起動時も同じ状態で開く（画角の再現性のため）
- 録画ボタン（タップで開始/停止）
- fps: 端末が対応していれば60fpsを優先。対応していなければ30fps
- **セルフ撮影用に3秒/5秒/10秒のカウントダウンタイマー**（スイングは自撮りが基本なので必須）
- **録画時間を 5/10/20/30秒 から選択できる**（既定10秒）。設定は保存する
  → カウントダウンと組み合わせて「5秒待って20秒録画」ができること。
    自撮りでは位置に入って構えて動く時間の余裕が要るため、長めに撮れることに実用上の価値がある
- 撮影後は自動でライブラリに保存

> **fpsの補足:** Flutterの`camera`プラグインは高fps（120fps以上のスローモーション）設定が弱い。
> ゴルフスイングは非常に速いため、より高精度に撮りたいユーザーには
> 「端末標準のカメラアプリでスロー撮影 → 本アプリに取り込む」導線を用意する。
> これがあるため**取り込み機能はv1で必須**。

### 3.3 比較画面（主役）

2本のクリップを A（基準）/ B（比較対象）として読み込む。
表示方法は **透過モード** と **分割モード** の2つを持ち、画面上部のセグメントコントロールで切り替える。

**モードを切り替えても、再生位置・同期設定・位置合わせの結果はすべて維持される**（作り直しさせない）。
下部のタイムライン操作系は両モードで完全に共通のものを使う。

#### 3.3.1 透過モード

- 映像エリアに A を表示し、その上に B を重ねる
- **透過スライダー**: B の不透明度 0〜100%。画面下部に大きく配置し、片手の親指で操作できる位置に置く
- 透過スライダーはこのモードでのみ表示する（分割モードでは意味がないので出さない）

#### 3.3.2 分割モード

- 画面を**上下に2分割**し、上に A、下に B を表示して同時再生する
- 分割比率は 50:50 固定（v1では仕切りのドラッグ変更はしない）
- **上下 / 左右の切替トグル**を用意する
  - レイアウトの軸を差し替えるだけなので実装コストはほぼゼロ
  - 縦持ちで人物全体を撮った映像は左右分割、横持ちで撮った映像は上下分割のほうが見やすく、
    どちらが良いかは撮り方次第なのでユーザーに選ばせる
- 各映像に対して個別にパン/ズームができる（被写体の大きさと位置を揃えるため。3.3.4と共通の仕組み）

#### 3.3.3 タイムライン（両モード共通）

- 共通のシークバー1本（現在のフレーム位置）
- **コマ送りボタン ◀ ▶**（1フレームずつ）。タップ領域は大きく
- 再生 / 一時停止 / **ループ再生**（デフォルトON）
- 再生速度: 0.25x / 0.5x / 1x

#### 3.3.4 同期合わせ（両モード共通・機能の生死を分ける部分）

2本の映像は撮影開始タイミングが必ずズレるため、この調整がないと比較が成立しない。
UIは以下の「基準フレーム方式」を採用する（オフセット数値を直接いじらせるより直感的）。

1. A を再生し、基準の瞬間（例: インパクト）で止めて「ここを基準にする」をタップ
2. B でも同じ瞬間で止めて「ここを基準にする」をタップ
3. 以降、2本はその基準フレームが揃った状態で連動する

#### 3.3.5 位置合わせ（アライメント・両モード共通）

三脚が完全に同じ位置でない限り、映像の画角は微妙にズレる。
透過モードでは重ねるために、分割モードでは被写体の大きさを揃えるために、どちらでも補正が要る。

- 各映像に対して **ドラッグで平行移動 / ピンチで拡大縮小 / 2本指回転**
  - 透過モードでは B のみ調整すれば足りるが、内部的には A/B それぞれが変換行列を持つ形にしておく
    （分割モードで両方いじれるようにするため。同じ仕組みを両モードで使い回す）
- 「位置合わせモード」のトグルでオン/オフ（通常時に誤操作しないよう分離する）
- リセットボタン
- 合わせた結果は比較ペアごとに保存し、次回同じ2本を開いたときに復元する

### 5.1 リリース戦略: Android先行（2026-07-17 決定）

**v1はAndroid版のみをリリースする。iOS版は売上を見てから判断する。**

**iOSの制約（調査済み・2026-07-17）:**

- iOSアプリのビルドとApp Store提出には**macOSが必須**。iPhone/iPadでは不可能。
- ただしMacの**所有**は必須ではない。クラウドビルド（Codemagic等）やリモートMacレンタル
  （MacinCloud等、月20ドル程度）で、Windowsからでも提出は可能。
- 手持ちのiPhone/iPadは**テスト機として有効**。TestFlight経由で実機テストができる。
  カメラアプリはシミュレータで検証しきれないため、iOS版に進む際は実機が必須になる。

**それでもAndroid先行にする理由:**

1. Play Consoleは25ドル買い切りのみ。売れるか分からない段階でMac代・Apple税を先払いしない
2. **本アプリはネイティブSwiftコードを含む**（フェーズ3）。純Dartアプリと違い、
   クラウドビルドだけの運用ではXcodeのデバッガ・クラッシュログが使えず、
   実機クラッシュ時の調査が極めて苦しくなる
3. フェーズ3のネイティブ実装をまずAndroid（Kotlin）側で完成させ、
   設計が固まってからiOS（Swift）に移植するほうが手戻りが少ない

**iOS版に進む場合の追加作業（v2以降）:**
Pigeonのインターフェースは共通のまま、`AVAssetImageGenerator` を使ったSwift実装を追加する。
Flutter側のコードは原則そのまま流用できる（この移植しやすさを保つことがフェーズ3の設計要件）。

**必ず押さえること:**
- プライバシーポリシーはデータ収集がなくても**必須**。「本アプリは一切のデータを収集しません。
  撮影した映像は端末内にのみ保存されます」で足りる。GitHub Pages等に置けば無料。
- 権限の用途説明文（iOS: `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription` /
  Android: CAMERA, READ_MEDIA_VIDEO）を用途が伝わる日本語で書く。ここが雑だとリジェクトされる。

## 6. Codexへの実装依頼の分割

一度に全部投げると破綻するため、以下のフェーズごとに指示書を切って渡す。
各フェーズの完了時に実機で動作確認してから次へ進む。

| # | フェーズ | 内容 | 完了の定義 |
|---|---|---|---|
| 1 | 土台 | Flutterプロジェクト雛形、ルーティング、Riverpod、クリップのデータモデルとJSON永続化、ライブラリ画面（ダミーデータで一覧表示・削除） | ライブラリ画面が起動し、ダミークリップの表示と削除ができる |
| 2 | 入力 | 撮影画面（camera + グリッドCustomPaint + タイマー）、取り込み（image_picker）。撮った/取り込んだ動画がライブラリに並ぶ | 実機で撮影・取り込みができ、ライブラリに反映される |
| 3 | ネイティブ層 | Pigeonでインターフェース定義、**Android(MediaMetadataRetriever)のみ**フレーム展開実装、キャッシュ管理と破棄。サムネイル生成と取り込み動画の`durationMs`の穴埋めもここ。iOS実装は空スタブ（未実装例外）に留め、インターフェースは将来のSwift実装をそのまま差し込める形にしておく | 動画1本を渡すとフレーム画像の連番パスが返る。単体テストあり |
| 3.5 | トリミング | 展開上限（10秒/600フレーム）を超えるクリップから、必要な範囲を切り出す。範囲を目で見て選ぶためフレーム展開が前提であり、フェーズ3より前には作れない | 30秒の録画から任意の数秒を切り出して展開できる |
| 4a | 比較画面・基盤 | 2クリップの読み込み、共通タイムライン（シークバー・コマ送り・ループ・速度）、基準フレーム同期、**位置合わせのデータモデルと永続化のみ**（操作UIは4b）。表示は4bで差し替える前提の仮表示 | 2本が同期して再生でき、コマ送りが1フレームずつ正確に動く |
| 4b | 比較画面・表示モード | 透過モード（重ね表示＋透過スライダー）と分割モード（上下2分割＋上下/左右トグル）、**位置合わせのジェスチャーUI**（ドラッグ/ピンチ/回転→4aの変換データを操作）。モード切替で状態が維持されること | 両モードが動き、切り替えても再生位置・同期・位置合わせが保たれる |

> **2026-07-18 追記（4a/4bの境界変更）:** 位置合わせの操作UIは表示モードと密結合のため、
> 4aでは変換データ（dx,dy/scale/rotation）のモデル・永続化・コントローラ状態のみを用意し、
> ジェスチャーUIは4bで実装する。4aの仮表示の上に作ると4bで作り直しになるため。
| 5 | 仕上げ | アイコン、スプラッシュ、権限説明文、パフォーマンス調整（imageCache）、ストア提出物 | ストア提出可能な状態 |

**Codexに徹底させるルール:**

- 1フェーズ = 1指示書。フェーズをまたぐ実装を勝手に始めない
- 動画プレイヤーを重ねる方式に勝手に変更しない（フレーム展開方式を厳守）
- ffmpeg系ライブラリを導入しない
- **透過モードと分割モードで再生ロジックを二重に書かない。**
  同期・コマ送り・ループ・速度・位置合わせは単一の共通コントローラが持ち、
  表示モードはその上に乗る薄い表示層として実装すること。
  ここを分けて書かせると、片方のモードだけ挙動がズレるバグが必ず出る
- 依存パッケージを追加する場合は理由を明示し、独断で増やさない
